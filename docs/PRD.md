## 1. 背景与问题

大学生周末想出去玩，但遇到的阻力主要有五个：

| # | 痛点 | 现状 | 我们的解法 |
|---|------|------|-----------|
| P1 | **信息分散** | 展览看公众号，市集刷小红书，演出上秀动/大麦，徒步翻两步路 | 按城市聚合"本周末可去"的活动，统一卡片结构 |
| P2 | **决策成本高** | 天气、预算、人数、开放时间要自己逐个查 | 多因子打分，给出**推荐理由 + 风险提示**，一键生成两天行程 |
| P3 | **没人一起** | 室友没空；剧本杀、飞盘凑不齐人 | 绑定活动的组队广场，显示"差几人"，并有安全机制 |
| P4 | **攻略不可信** | 种草笔记广告多，与学生预算不符 | 同城学生写的、带真实花费的攻略，可按"最省钱"排序 |
| P5 | **玩完就忘** | 照片散在相册，没有记录感 | 打卡时间线、徽章、城市探索进度；打卡一键转攻略 |

**一句话定位**：*帮大学生用最低决策成本，找到这个周末能去、去得起、有人陪的事。*

## 2. 目标与成功指标

### 2.1 产品目标（MVP，单城市试点 8 周）
1. 验证「推荐 → 出发」转化：用户看完推荐后，确实会去
2. 验证组队需求：活动绑定的组队能成团
3. 跑通内容飞轮：打卡 → 攻略 → 被下一位用户使用

### 2.2 指标体系

| 层级 | 指标 | 定义 | MVP 目标【待对齐】 |
|------|------|------|-------------------|
| 北极星 | **周末成行人数** | 每周末产生打卡或组队成团的去重用户数 | 试点校周活的 15% |
| 发现 | 推荐点击率 | 首页活动卡片点击 / 曝光 | ≥ 12% |
| 发现 | 收藏/加入行程率 | 详情页 → 收藏或加入行程 | ≥ 20% |

## 4. 竞品分析

> 原文档里的竞品列表我看不到；下面是按"能被用户替代的方案"选的，请补充或替换【待对齐】。

| 竞品 | 解决什么 | 强项 | 对学生周末场景的短板 | 我们借鉴 / 差异化 |
|------|---------|------|------------------|-----------------|
| **小红书** | 种草、攻略 | 内容量大，视觉强，搜索心智强 | 信息不结构化（时间、价格、是否开放要自己找），广告多，看完不知道"这周末能不能去" | 借鉴：图文卡片、收藏夹。差异：结构化字段 + 时效 |
| **大众点评 / 美团** | 商户评价、团购 | POI 全、交易闭环 | 以商户为中心而非"活动"，没有时效活动，社交弱 | 借鉴：评分、人均、营业时间字段 |
| **豆瓣同城** | 同城活动 | 文艺活动多，"感兴趣/要参加" | 产品基本停更，供给萎缩，没有推荐 | 借鉴："想去/去过"的状态设计；**它留下的空位就是机会** |
| **活动行 / 互动吧** | 活动发布报名 | 报名、票务、签到工具链 | 偏 B 端工具，C 端浏览体验差 | 借鉴：报名、签到、名额状态 |
| **秀动 / 大麦** | 演出票务 | 票务独家 | 只覆盖演出 | 外链购票，不自建票务 |
| **两步路 / 六只脚** | 户外轨迹 | 轨迹、难度 | 门槛高，偏硬核 | 借鉴：难度分级、安全提示 |
| **搭子类（如 Soul 兴趣群、各类找搭子小程序、校园墙）** | 找同伴 | 需求真实、量大 | 安全风险高，容易变社交/约会，与活动脱钩 | 差异：**队伍必须绑定具体活动 + 学生认证 + 行程报备** |
| **Meetup（海外）** | 兴趣小组线下活动 | 小组长期运营、RSVP | 国内无 | 借鉴：RSVP 状态、组织者信誉 |

**结论：我们的切口 = 时效性的结构化活动库（解决 P1/P2）+ 绑定活动的组队（解决 P3）+ 带真实花费的学生 UGC（解决 P4/P5）。** 不和小红书拼内容量，也不和点评拼 POI 覆盖，只做「这个周末、学生、本地」这一个窄场景，做透。

## 5. 内容产品思路（产品 sense）

### 5.1 内容是什么：两类内容，两套逻辑
- **活动（结构化、时效）**：PGC/运营为主，强调**准确**。字段必须完整，过期自动下线。
- **攻略 / 打卡（非结构化、长尾）**：UGC 为主，强调**真实**。每篇攻略必须关联至少 1 个活动，并带真实花费。

### 5.2 冷启动供给（最关键的风险）
1. **单城单校起步**：先选 1 个城市、3–5 所高校，运营人工维护 80–150 条"常驻 + 本周限定"活动
2. **供给来源**：运营人工录入 → 校园社团 / 市集主理人自主提交（经审核）→ 后期公众号、票务平台聚合
3. **种子攻略**：招募 20–30 名校园体验官，每人每月 2 篇带花费的攻略，给予徽章和活动票作为激励
4. **组队冷启动**：运营账号发起"官方局"（飞盘、徒步、剧本杀），保证每周末广场上都有可加入的队

### 5.3 内容质量机制
- **结构化优先**：发布攻略时强制填写「总花费、人数、时长、关联活动」，正文自由写。这些字段让"最省钱"排序、行程生成成为可能，也让内容不容易变成广告
- **时效标识**：活动卡片显示"本周末可去 / 仅周六 / 即将结束 / 已结束"
- **真实性信号**：攻略作者显示"已打卡该活动"标签（有对应打卡记录才显示）；学生认证标识
- **排序**：攻略默认按 `热度 = 点赞×1 + 收藏×3 + 照着去玩×5`，叠加时间衰减；提供"最省钱""最新"
- **反广告**：商业合作必须打"合作"标签；同一外链高频出现进入人工审核

### 5.4 飞轮

```
发现(推荐/行程) → 组队(找搭子) → 出发 → 打卡(记录/徽章)
      ↑                                          ↓
      └──── 攻略被检索、被"照着去玩" ←──── 打卡一键转攻略
```

每个环节都要把用户推向下一步：详情页有"去组队"，组队结束后提醒打卡，打卡完成后提示"转成攻略可以帮到 xx 位想去的同学"。

## 8. 状态定义

> 原文档里的状态定义我没有看到，下面是建议版本，需要和原文逐个核对【待对齐】。

### 8.1 活动（Activity）

| 状态 | 含义 | 前台可见 | 进入条件 |
|------|------|---------|---------|
| `draft` 草稿 | 运营或提交方编辑中 | 否 | 新建 |
| `pending_review` 待审核 | 已提交 | 否 | 提交 |
| `rejected` 审核驳回 | 信息不全或不合规 | 否（提交方可见驳回原因） | 审核不通过 |
| `upcoming` 即将开始 | 已上线，开始时间在未来 | 是 | 审核通过且开始时间 > 当前 |
| `ongoing` 进行中 | 在开放时间段内 | 是 | 当前时间落在开放时间段内 |
| `ending_soon` 即将结束 | 距结束 ≤ 7 天（展览、限时市集） | 是，带"即将结束"标签 | 定时任务 |
| `ended` 已结束 | 已过结束时间 | 列表不出现；详情可从攻略进入，显示"已结束" | 定时任务 |
| `offline` 已下架 | 被举报核实或主动下架 | 否 | 运营操作 |

常驻类活动（公园、CityWalk）没有结束时间，只在 `ongoing` 和 `offline` 之间切换；"本周末是否开放"由 `open_days` 和闭馆日计算。

```
draft → pending_review → upcoming → ongoing → ending_soon → ended
              ↓              ↘___________↘__________↘→ offline
           rejected → draft
```

### 8.2 队伍（Team）

| 状态 | 含义 | 可加入 | 进入条件 |
|------|------|-------|---------|
| `recruiting` 招募中 | 未满员、未截止 | 是 | 发布成功 |
| `full` 已满员 | 成员数 = 上限 | 否（可排候补，P1） | 有人加入后满员；有人退出则回到 `recruiting` |
| `locked` 已成团 | 截止时间到且人数 ≥ 最低成行人数，或发起人手动确认 | 否 | 截止或手动操作 |
| `in_progress` 进行中 | 到了集合时间 | 否 | 定时任务 |
| `completed` 已完成 | 活动结束 | 否 | 集合时间 + 活动时长，或全员签到后结束 |
| `failed` 未成团 | 截止时人数不足 | 否 | 定时任务；通知全部成员 |
| `cancelled` 已取消 | 发起人取消，或发起人退出且无人接任 | 否 | 手动操作。成团后取消扣发起人信誉分 |
| `banned` 已封禁 | 被举报核实 | 否，前台隐藏 | 运营操作 |

```
recruiting ⇄ full
    │          │
    └─(截止)───┴──→ locked → in_progress → completed
    │                 │
    ├─(人数不足)→ failed
    └─(发起人取消)→ cancelled  ←────┘
任意状态 ──(违规)──→ banned
```

**成员状态**（TeamMember）：`applied` 申请中（需审核时） → `joined` 已加入 → `checked_in` 已签到 / `no_show` 爽约；另有 `left` 主动退出、`removed` 被移出、`rejected` 申请被拒。

### 8.3 攻略（Guide）

| 状态 | 含义 | 可见 |
|------|------|-----|
| `draft` 草稿 | 未提交 | 作者 |
| `pending_review` 审核中 | 机审 + 人审 | 作者（显示"审核中"） |
| `published` 已发布 | 公开 | 所有人 |
| `rejected` 未通过 | 附原因，可修改后重新提交 | 作者 |
| `hidden` 已隐藏 | 被举报核实或作者设为私密 | 作者 |
| `deleted` 已删除 | 软删除，保留 30 天 | 无 |

机审命中低风险规则时可"先发后审"，命中外链或敏感词时"先审后发"。

### 8.4 打卡（Checkin）
`private` 仅自己（默认） / `public` 公开 / `deleted`。公开打卡会出现在活动详情的"大家的打卡"里。

### 8.5 用户认证（UserVerification）
`unverified` → `pending` → `verified` / `rejected`（可重新提交）；`verified` 每学年需要复核一次（毕业后变为 `alumni`，不能加入学生专属队伍）。

### 8.6 行程报备（SafetyReport）
`scheduled` 已报备 → `active` 进行中（出发时间到） → `returned` 已平安返回（用户点"我到了"）；超过预计返回时间 1 小时仍未确认 → `overdue`，提醒用户本人，再过 30 分钟提醒紧急联系人（P1）。

## 9. 推荐规则（MVP 规则版）

与现有原型保持一致，后续再换成模型：

| 因子 | 规则 | 分值 | 转成用户文案 |
|------|------|------|------------|
| 基础分 | — | 50 | — |
| 兴趣 | 命中兴趣标签 | +22 | "你喜欢展览" |
| 预算 | ≤ 日预算 / 超出 | +12 / −25 | "免费" "预算很宽裕" / "超预算 ¥xx" |
| 学生价 | 用户是学生且有学生价 | +5 | "学生价" |
| 人数 | 匹配 / 人数不足 / 人数偏多 | +8 / −6 / −8 | "适合你们人数" / "需 N 人，可去组队" |
| 天气 | 雨天室内 +15、户外 −20；高温室内 +10、户外 −8；晴天户外 +10 | — | "室内不怕雨" / "雨天慎选" |
| 开放日 | 当天不开放 | −40 | "周六不开放" |
| *（P1 新增）* 时效 | 即将结束 | +8 | "还剩 3 天" |
| *（P1 新增）* 社交证明 | 同校有人收藏或组队 | +5 | "有 3 位同校同学想去" |
| *（P1 新增）* 多样性 | 前 10 条中同类型不超过 3 条 | 重排 | — |

分数截断在 1–99。**每一项加减分都必须能翻译成一句用户看得懂的话**，这是推荐可信度的来源，也是区别于信息流的产品特征。

## 11. 关键流程

**首次使用**：落地页 → 偏好引导（可跳过，跳过时用默认值） → 发现页（已带推荐理由） → 点卡片 → 详情 → 收藏（拉起登录）

**找搭子**：详情页"去组队" → 有队伍就列出可加入的队，没有就引导"发起一个" → 未认证时拉起学生认证 → 加入成功，提示设置行程报备 → 出发前 2 小时推送集合提醒 → 结束后推送"去打卡"

**内容沉淀**：打卡完成 → 提示"转成攻略" → 预填表单 → 发布 → 审核 → 出现在该活动的详情页和攻略列表

## 12. 非功能需求
- **形态**：移动端优先的 H5 / PWA（现有原型是纯静态 SPA），后续视需要做微信小程序（分享与登录更顺）
- **性能**：首屏 < 2s（4G）；图片上传前压缩到长边 1080px 以内
- **隐私**：手机号不对外展示；定位只在签到时使用；打卡默认私密；符合《个人信息保护法》，要有隐私政策和账号注销入口
- **合规**：UGC 需要内容安全审核（机审 + 人审）；如果做小程序，需要相应类目资质
- **可运营**：活动、队伍、攻略、举报都要有后台（MVP 可以先用低代码表格后台）

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 活动供给不足或过期 | 推荐不准，用户流失 | 单城起步、运营每周三更新"本周末"、过期自动下线、用户可"报错" |
| 组队安全事件 | 致命 | 强制学生认证、绑定活动、公共场所集合提示、行程报备、举报快速处理、不鼓励夜间一对一 |
| 组队变成交友软件 | 社区调性失控 | 队伍必须绑定活动；没有私信，只有队内群聊；不做颜值、照片墙 |
| UGC 广告化 | 信任崩塌 | 结构化花费、"已打卡"标识、合作标签、外链审核 |
| 周末之外无打开理由 | 留存低 | 周三"本周末预告"推送、展览"即将结束"提醒、组队动态通知 |
